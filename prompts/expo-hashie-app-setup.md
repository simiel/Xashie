# Expo Hashie app setup

## Goal

Create the initial React Native mobile application for Hashie inside `apps/hashie`, using Expo and Expo Router as the foundation for onboarding, accessibility, conversation, preferences, and the future user experience.

## Skills and guidance

- Expo `building-native-ui` skill: use Expo Router, stack layouts, responsive scrolling, safe-area-aware layout, and native-compatible styling.
- Use Expo Go as the first verification target; do not create a custom native build unless the scaffold requires native functionality unavailable in Expo Go.

## Inspected project state

- Repository: `/Users/samuel/Desktop/projects/Xashie`
- Existing application code, package manifests, dependencies, and tests: none found
- Existing structure: `apps/hashie`, `apps/operations`, `apps/backend`, `artifacts`, `packages`, `prompts`, and `.agents`
- Existing `apps/hashie/.gitkeep` is a placeholder and may be replaced by the generated Expo project files.

## Decisions

- Scaffold a TypeScript Expo app in `apps/hashie`.
- Use Expo Router with a root route and a minimal, accessible starter screen that identifies Hashie as a Ghana-focused health education and support prototype.
- Keep the initial scope limited to the app foundation: project manifest, Expo configuration, TypeScript configuration, router entry point, and starter assets/config generated by the official Expo scaffold.
- Keep all backend, authentication, AI, health knowledge, and persistence work out of this task.
- Do not add Clerk, Supabase, AI SDK, provider keys, environment secrets, or production deployment configuration yet.
- Preserve the existing repository-level structure and `AGENTS.md`.

## Requirements

1. `apps/hashie` is a runnable Expo TypeScript project.
2. The app has a route matching `/` through Expo Router.
3. The starter screen is readable, responsive, and accessible with selectable important text and no clipped content.
4. The project uses kebab-case filenames where new custom files are introduced.
5. The client contains no direct model, MCP, privileged-tool, or database calls.
6. No secrets or credentials are committed.

## Security and privacy

- Do not include real health data, user data, credentials, API keys, or tokens.
- Keep the mobile app as a presentation and interaction layer; future writes and privileged actions must go through the backend API.
- Use placeholder copy that does not present the prototype as a clinician, emergency service, or diagnostic system.

## Acceptance criteria

- Expo dependency metadata and configuration exist under `apps/hashie`.
- TypeScript source compiles.
- Expo Router resolves the root route.
- The project can start with Expo Go using `npx expo start`.
- The starter experience clearly communicates Hashie’s purpose and limitations without claiming clinical authority.
- Existing files outside `apps/hashie` and this prompt are unchanged.

## Checks

- Run the project’s TypeScript check, if provided by the generated project.
- Run Expo’s project diagnostics or equivalent available check.
- Start the project with `npx expo start` and verify it reaches the Expo development server; stop it cleanly after verification if no interactive device is available.
- Review `git status --short` and confirm changes are scoped to `apps/hashie` and this prompt.
- Confirm no `.env` files, secrets, or credential-like files were created.

## Manual verification

1. In Expo Go, open the development server for `apps/hashie`.
2. Confirm the root screen renders without a red error screen.
3. Confirm the Hashie title, purpose, and limitation text are visible at normal and larger text sizes.
4. Confirm the screen remains usable on a narrow phone viewport and can scroll if content grows.
5. Confirm important text can be selected or copied where supported.

## Implementation scope after approval

Use the official Expo scaffolding workflow in `apps/hashie`, then make only the minimal starter-screen and router adjustments needed to satisfy this prompt. Do not implement later product features as part of the scaffold.
